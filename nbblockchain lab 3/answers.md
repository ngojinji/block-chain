**Avalanche effect:** changing only one character (`B` → `b`) produces a completely different hash; the two digests share no visible pattern.

### Q1. Each extra leading zero multiplies expected work by ≈ how much? Why?

**≈ 16×.** Each hex digit of a SHA-256 output takes one of 16 values with (practically) uniform probability. The chance that a random hash starts with *k* zero hex digits is 16⁻ᵏ, so the expected number of attempts is 16ᵏ. Each extra zero therefore multiplies expected work by 16.

The measured nonces fluctuate because mining is a random process (e.g. k=2 and k=3 both hit at nonce 61 by luck), but the trend is clear: k=6 needed ~24.5 million tries vs. ~14 thousand for k=4.

### Q2. Verifying the found nonce takes how many hash calls? What does this say about PoW?

**One hash call.** The verifier computes `sha256(data + nonce)` once and checks the leading zeros. PoW is **hard to find but trivial to verify**: miners spend huge amounts of computation, while any node can check the result almost for free. This asymmetry is what lets every node in the network cheaply validate blocks without trusting the miner.

### Q3. For n = 1,000,000 transactions, how many hashes does one proof contain?

**20 hashes**, since ⌈log₂(1,000,000)⌉ = 20 (2²⁰ = 1,048,576). A proof holds one sibling hash per tree level, so its size grows logarithmically: about 20 × 32 bytes = 640 bytes, instead of the whole transaction list.

### Q4. A real system that uses exactly this mechanism

**SPV (Simplified Payment Verification) in Bitcoin.** A light wallet stores only block headers (80 bytes each), not full blocks. To confirm that a transaction is in a block, it asks a full node for the Merkle proof (the sibling hashes from the transaction up to the root). The wallet recomputes the path and compares the result with the Merkle root in the block header. If they match, the transaction is in the block, and the wallet never had to download the other transactions.

(Other examples: airdrop claims where the contract stores only the Merkle root and each user submits a proof of eligibility; exchange proof-of-reserves.)

(The key is generated fresh with `Account.create()` on each run, so the address differs between runs. To test determinism, the script signs the same message twice with the **same** key.)

### Task 1. Same message twice — is the signature identical? Which RFC explains this?

**Yes, identical.** ECDSA needs a secret nonce *k* for every signature. eth-account derives *k* deterministically following **RFC 6979**: *k* = HMAC-DRBG(private key, message hash). Same key + same message → same *k* → same (r, s, v).

This matters for security: if *k* were ever reused for two different messages, or generated by a weak RNG, the private key could be computed from the two signatures (as happened with the Sony PS3 signing key). RFC 6979 removes the dependence on a good random number generator.

### Task 2. The tampered message recovers a different address — why does this prove integrity?

Changing one character (`Buoi 3` → `Buoi 4`) changes the message hash completely (avalanche effect). ECDSA recovery uses both the signature (r, s, v) and the message hash to compute a public key. With a different hash, the same signature produces a **different public key**, and therefore a different address that does not match the signer.

So a signature is valid only for the exact message that was signed. Any modification, even a single character, is detected because the recovered address no longer matches the expected signer. This gives **integrity** (the message was not changed) and **authentication** (only the holder of the private key could have produced it).
